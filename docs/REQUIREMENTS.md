## 1. 产品定位

Backup Studio 是一个**高性能本地目录备份工具**。核心命题是：在目标介质随时可能被拔出的前提下，用最少的 I/O 完成一次可信的镜像备份。

关键设计前提：

| 前提 | 含义 |
| --- | --- |
| 目标介质不可靠 | 写入必须原子落盘，中断可续，拔盘可恢复 |
| I/O 成本高于 CPU 成本 | 判定顺序按 I/O 代价从低到高排列，能用元数据判定的绝不算哈希 |
| 内容相同即同一份数据 | 文件改名不应触发重新拷贝 |
| 状态来自真实事件 | 进度、吞吐、介质状态均由磁盘实际完成量与真实探测驱动，不做前端定时器伪造 |

#### 3.0 关键修订说明

本条替代原方案中「可逆/不可逆二分判定」「自动修复默认」「分区表自动恢复」「FTL 修复」等高风险表述。核心修订为七条：

1. **三态判定**替代可逆/不可逆二分
2. **默认只读**
3. **副本优先**
4. **修复分级**
5. **备份集一致性优先**
6. **隔离观察可撤销**
7. **本机事务日志权威**

**边界声明**：本软件不进行硬件修复，不操作 SSD FTL/固件，不默认自动执行文件系统/分区表高危修复。

#### 3.1 背景与目标

**背景**

备份软件在写入移动介质过程中可能遭遇突发拔盘、断电、USB 异常、写保护、文件系统元数据损坏、备份分片截断、索引不一致等问题。部分为逻辑层可恢复问题，部分为物理/固件/FTL 层不可逆问题。软件必须区分处理，避免将逻辑损伤修成物理损伤或数据丢失。

**目标**

- 拔盘后能可靠保存断点，重新插入后自动检测、分类、受控恢复
- 优先保障备份集可恢复性，而非「修好整块盘」
- 默认只读检测；仅对明确安全的备份集分片/索引问题执行自动修复
- 对疑似物理故障、固件异常、FTL 异常、持续 IO 错误，停止写入、告警、隔离并切换备用介质
- 所有判定输出证据链，隔离标记可撤销，高危修复必须用户确认

**非目标（本软件明确不做）**

- 不进行芯片、盘片、颗粒、磁头等硬件修复
- 不操作 SSD FTL 表、固件、主控缓存内部元数据
- 不默认自动修复分区表/GPT，不默认后台静默执行 `chkdsk /f`、`fsck -y` 等高危写操作
- 不承诺恢复盘上与本软件无关的用户文件
- 不把「盘能识别」等同于「盘健康」，也不把「软件标记」等同于「物理坏盘」

#### 3.2 损伤范围与判定等级

**可处理/可辅助处理的损伤范围**

- 本次备份会话中断、分片截断、分片缺失、hash 校验失败
- 备份索引不完整、本机断点日志与盘上索引不一致
- 应用层缓存未刷盘导致的备份集校验异常（仅应用层补偿）
- 文件系统挂载失败、RAW 分区等：仅做只读检测，并调用系统工具进行受控人工确认修复
- 临时写保护、USB 枚举异常等接口/临时异常：仅做重枚举、只读校验与隔离观察

**不处理的损伤范围**

- 物理坏道、磁片刮伤、颗粒硬坏、主控硬件报错
- SSD FTL 元数据损坏、固件锁死、主控缓存未落盘的底层修复
- 分区表/GPT 的自动写回修复

**三态判定等级**

| 等级 | 名称 | 含义 | 软件动作 |
| --- | --- | --- | --- |
| L0 | 安全自动处理 | 证据表明问题集中在备份集分片/索引/应用层缓存，且介质基础读取稳定 | 可自动执行：分片重传、索引重建、应用层 sync、只读校验、恢复备份；**不写文件系统元数据** |
| L1 | 需人工确认 | 涉及文件系统修复、分区表恢复、全盘 `chkdsk`/`fsck`、写保护解除尝试等高风险操作 | 默认只读导出证据；用户明确确认并二次确认后，方可调用系统工具；全程审计 |
| L2 | 禁止写盘并隔离 | 大量持续 IO 错误、SMART 新增坏块/介质错误激增、随机断连、多次重试无法稳定识别 | 停止写入、告警、切换备用介质、标记「隔离观察」；禁止自动修复 |

判定必须输出：**等级、置信度、证据列表、建议动作**。不确定时默认 L1 只读，不得自动写盘。

#### 3.3 总体设计原则

1. **默认只读**：介质重新插入后先阻止/避免系统自动挂载写入，采集证据并校验，再决定是否写
2. **副本优先**：优先使用本机断点日志、其他介质副本、已完整分片恢复备份；盘修复是最后手段
3. **本机日志权威**：断点/索引日志双写本机与盘上，本机为权威，盘上为辅助；以「最后已提交事务」为准
4. **分片原子提交**：临时分片 → fsync → hash → 原子 rename → 目录 fsync → 索引事务提交
5. **修复分级**：L0 可自动；L1 必须确认；L2 禁止写盘
6. **证据链告警**：L1/L2 判定必须带原始证据、重试记录、换口换线结果；隔离标记可撤销
7. **保留上一完整恢复点**：任何强一致策略不得废弃唯一完整备份集
8. **备用介质预检**：切换前校验备用介质可达、容量、权限、独立备份链
9. **最小权限与命令白名单**：底层读取与系统修复工具调用需权限申请、设备路径校验、防注入、日志脱敏

#### 3.4 状态机与并发控制

**介质/会话状态流转**

```
正常备份 → 中断待校验 → 只读检测中 → 待用户确认 / 自动修复中 / 隔离观察
                                                  ↓
                              校验通过恢复备份 / 人工介入
```

**并发要求**

- 同一介质同一时间只允许一个备份或修复任务
- 检测、修复、备份互斥；修复期间禁止新备份写入该介质
- 设备身份使用「序列号 + 容量 + 接口类型 + 历史指纹」综合匹配；序列号不可读时进入人工确认，不得强行匹配

#### 3.6 功能需求详述

**FR-01 热插拔监听与中断标记（P0）**

- 监听 USB 移除/插入事件（Windows `WM_DEVICECHANGE`、Linux udev 等），记录中断时间、正在写入分片 ID、会话 ID、设备身份
- 拔盘后立即暂停备份进程，向本机写入「中断-待校验」事务日志；盘上轻量日志尽力写，不作为唯一依据
- 验收：拔盘后本机日志存在最后已提交分片与当前写入分片记录；重启软件后状态可恢复

**FR-02 双写事务日志（P0）**

- 关键断点、分片 hash、索引、会话状态双写本机与介质
- 日志字段至少包含：会话 ID、设备指纹、分片序号、分片状态、hash、事务序列号、CRC、提交标记、时间、版本
- 冲突解决以本机最后已提交事务为准；盘上日志仅作候选证据
- 验收：模拟盘上索引截断，软件仍能依据本机日志识别完整分片与缺失分片

**FR-03 分片原子提交（P0）**

- 备份文件分片化，分片大小可配置；FAT32 等限制下自动调整
- 每分片写入临时文件 → fsync → 计算 hash → 原子 rename → 目录 fsync → 索引事务提交
- 大段写入间按配置主动 sync；加密/压缩流式备份需在能力矩阵中标注是否支持断点续传，不支持则明确整组重传
- 验收：拔盘最多导致当前未提交分片残缺；已提交分片 hash 稳定且可识别

**FR-04 重新插入后只读检测与防自动挂载（P0）**

- 重新插入后优先阻止系统自动挂载/索引/写入；无法阻止时至少先采集只读证据并提示用户
- 进入「只读检测中」，禁止自动修复写盘
- 验收：重插后软件先完成设备识别与只读检测，未用户确认前不执行文件系统写操作

**FR-05 基础可达性与接口诊断（P0）**

- 检测设备枚举、基础扇区读取、序列号读取
- 识别失败时执行有限重试，并提示换线、换口、换主机；记录结果
- 设置重试上限，避免机械盘反复敲盘、SSD 反复映射
- 多次重试仍无法稳定识别，或盘自检/SMART 返回硬件报错，进入 L2
- 验收：短暂枚举失败可继续检测；持续失败输出 L2 证据并禁止写盘

**FR-06 逻辑健康检测（P0）**

- 只读读取分区表（MBR/GPT）并校验；读取文件系统超级块/元数据状态；调用系统工具做只读预检查
- 读取备份索引，校验分片 hash，标记完整/截断/缺失/索引不一致
- SMART 只读查询并建立基线；无 SMART 能力时明确标注「能力缺失」，不得伪造健康结论
- 验收：检测结果包含分区、文件系统、分片、索引、SMART/接口证据

**FR-07 三态风险判定器（P0）**

- 输入：设备枚举稳定性、IO 错误、重试记录、SMART 基线对比、损坏范围、分片/索引状态、文件系统状态、接口诊断结果
- 输出：L0/L1/L2、置信度、证据链、建议动作
- 规则必须可解释、可审计；评分器不得作为唯一依据
- 验收：不确定场景默认 L1 只读；L2 判定附证据；判定结果可导出

**FR-08 副本优先恢复与备份集修复（L0，P0）**

- 优先从本机日志、其他介质副本恢复备份集
- 对 L0 场景，仅修复本软件备份集：保留完整分片，丢弃截断分片，标记缺失分片，按用户配置执行：
  - **策略 A 断点续传**：只重传缺失/截断分片，完成后分层校验
  - **策略 B 强一致**：废弃当前中断备份组并重新完整备份，但必须保留上一完整恢复点
- 修复前将受影响索引/元数据/分片清单快照到本机；修复后重写一致索引并双备份
- 验收：只重传残缺分片；上一完整备份集不被删除；修复后 hash 校验通过

**FR-09 文件系统/分区表高危修复入口（L1，P0）**

- 文件系统修复：默认只读预检；用户明确选择作用分区并二次确认后，方可调用系统 `chkdsk`/`fsck`；提示可能影响同分区其他文件；执行前镜像关键扇区/元数据到本机；记录免责确认
- 分区表恢复：默认不自动执行；仅提供证据导出与人工修复向导；如提供写回功能，必须二次确认、CRC 校验、主备头一致性检查、先镜像受影响扇区
- 验收：未确认不执行任何文件系统写修复；执行记录含用户确认、命令、作用范围、镜像路径

**FR-10 应用层缓存/FTL 相关异常处理（L0/L2，P0）**

- 触发 flush/sync，尽力将 OS 层缓存刷到介质
- 重新执行分层校验，找出不一致分片，按 FR-08 处理
- 明确提示：应用层无法修复 SSD 主控 FTL；sync 后仍大量持续异常，升级 L2 隔离
- 验收：不出现「修复 FTL」功能入口；持续异常进入 L2

**FR-11 写保护/临时异常处理（L1/P1）**

- 提供一键重枚举入口；提示换口换线换主机
- 只读全量/分层校验；通过则解除灾备标记；失败走 FR-08 或 L2
- 多次出现标记「隔离观察」，可人工撤销；不得直接永久标记坏盘
- 验收：隔离标记可撤销且有证据；不尝试固件解锁

**FR-12 隔离观察与备用介质切换（P0）**

- L2 时停止写入该介质，禁止继续备份，告警并切换备用介质
- 切换前预检备用介质可达、容量、权限、独立备份链；失败则告警并保留现场
- 隔离标记命名「高风险/隔离观察」，非「物理坏盘」
- 验收：L2 不写盘；备用介质不可用时明确告警；隔离可撤销

**FR-13 告警与证据链（P0）**

- 告警包含：判定等级、证据、建议、受影响备份集、备用介质切换结果、人工入口
- 支持导出诊断包：日志、SMART、IO 错误、分片清单、索引快照、用户确认记录
- 验收：诊断包可离线分析；敏感路径/密钥脱敏

**FR-14 用户交互（P0）**

默认交互改为「安全模式默认」，四档：

1. **安全模式（默认）**：只读校验 + 副本恢复 + 导出日志，不写盘
2. **仅修复本软件备份集**：断点续传/索引重建，需确认
3. **高级文件系统修复**：调用系统工具，高危二次确认 + 免责
4. **仅导出日志、人工处理**

验收：默认不触发高危写操作；所有高危操作有二次确认。

**FR-15 权限与安全（P0）**

- 底层磁盘读取、系统修复工具调用需管理员/root 权限；非权限时降级为只读检测并提示
- 使用最小权限辅助服务、命令白名单、设备路径校验、参数转义、日志脱敏
- 验收：无权限不崩溃；命令不可注入；日志不含明文密钥

**FR-16 跨平台能力矩阵（P1）**

- 按 Windows/Linux/macOS、USB 桥接/SATA/NVMe、文件系统类型（NTFS/ext4/exFAT/APFS 等）列出：可检测、可自动处理、仅告警、不支持
- 加密容器、VHD、压缩包内文件系统等标注「不支持直接 fsck」
- 验收：能力矩阵随版本发布；不支持场景有明确提示

**FR-17 审计与状态可恢复（P0）**

- 记录检测、判定、用户确认、修复命令、快照、校验结果、隔离/撤销操作
- 软件重启后状态机可恢复，不重复执行高危操作
- 验收：审计日志完整；重启后不误触发修复

#### 3.7 核心流程

**6.1 正常备份流程**

分片临时写 → fsync → hash → 原子 rename → 目录 fsync → 索引事务提交 → 双写日志。大段写入间按配置 sync。

**6.2 拔盘中断流程**

热插拔监听 → 暂停备份 → 本机写「中断-待校验」事务 → 记录当前分片与会话 → 盘上日志尽力写。

**6.3 重插检测流程**

阻止自动挂载/只读 → 设备指纹匹配 → 接口诊断 → 只读健康检测 → 三态判定 → 输出证据与建议。

**6.4 分支处理**

- **L0**：快照受影响索引/清单 → 副本优先 → 分片重传/索引重建 → 分层校验 → 恢复备份
- **L1**：只读导出证据 → 用户选择作用范围 → 二次确认 → 镜像关键扇区 → 调用系统工具 → 记录审计 → 校验 → 人工复核
- **L2**：停止写盘 → 告警 → 预检备用介质 → 切换 → 隔离观察 → 人工入口

**6.5 退出灾备**

校验通过且索引一致后退出灾备模式；修复失败但判定逻辑损坏时保留现场日志，进入人工介入。

#### 3.8 非功能需求

| 维度 | 要求 |
| --- | --- |
| 性能 | 检测阶段只读；全量校验可配置为分层校验（分片 hash → 索引 Merkle/清单 → 抽样/全量）；重试有上限 |
| 可靠性 | 日志事务化、原子提交、断电/拔盘后可恢复；不因检测导致二次写入 |
| 安全 | 最小权限、命令白名单、设备路径校验、日志脱敏、高危操作免责确认 |
| 兼容性 | 跨平台能力矩阵；无 SMART/无权限时明确降级 |
| 可用性 | 默认安全模式；普通用户不被引导执行全盘修复；高危操作有风险说明 |
| 可维护性 | 判定规则可配置、可解释、可审计；诊断包可导出 |

#### 3.9 验收标准（关键场景）

1. 备份中拔盘，本机日志记录最后已提交分片与当前分片；重启后状态可恢复
2. 重插后软件先只读检测，未确认前不执行文件系统写修复
3. 盘上索引截断时，软件依据本机权威日志识别完整/截断/缺失分片
4. L0 场景仅重传截断/缺失分片，完整分片不重传；上一完整备份集保留
5. L1 场景未二次确认不执行 `chkdsk`/`fsck`；执行前有快照与审计
6. L2 场景停止写盘、告警、切换备用介质；备用不可达时明确告警
7. 隔离标记可撤销，带证据，不显示「物理坏盘」结论
8. 无管理员权限时只读检测可用，高危操作提示权限不足
9. 诊断包可导出且敏感信息脱敏
10. 加密/压缩流式备份在能力矩阵中明确断点续传支持情况；不支持时整组重传且保留上一完整恢复点

#### 3.10 禁止事项

1. 禁止默认自动修复分区表/GPT
2. 禁止后台静默执行高危文件系统修复
3. 禁止提供「修复 SSD FTL/固件」功能入口

**实测暴露的三个真实问题**

1. **续传点内容会损坏，且当前无法定位损坏位置**
   拔盘时 U 盘写缓冲丢失部分扇区，导致 `.part` 文件**长度正确（47 MB）但内容有洞**。账本记的是 60 MB，磁盘实际只有 47 MB——证明「以磁盘为准」是必要的。
   续传后 SHA-256 与回读校验不符 → 判定 `VERIFY_FAILED` → 丢弃临时件**整份重传**。
   代价：先写完 256 MB 再全部丢弃重写，实际磁盘写入量超过从头重传。
   **根因是缺少 FR-03 分片化**：整文件粒度下无法定位受损区间，只能整份重来。分片级 hash 才能做到「只重传受损分片」。
   **第二阶段已修复**：改为按 1 MiB 分片逐片 SHA-256 比对，只重写损坏/截断/缺失的分片，详见 §3.15。

2. **恢复后账本状态与实际不符**（已修复）
   `recover()` 原先在 `await start()`（阻塞至备份结束）之后才应用续传进度，此时 `.part` 已被 `finalize()` 删除 → `copiedBytes` 归零，且把已完成任务的 `status` 从 `done` 覆盖回 `copying`。若此刻崩溃，续传会重复备份已完成文件。
   **修复**：续传起点改为在 `enqueueCopy` 派发前按磁盘实际字节计算（`StartOptions.resumeTasks`），删除事后的补偿逻辑。
   **第二阶段重构**：续传粒度下沉到工作线程（按分片比对），服务层的 `resumeTasks` 随之移除，改由 `StartOptions.resume` 布尔开关驱动。

3. **盘上日志临时件残留**（已修复）
   移动介质上 `rename` 偶发失败（目标文件被索引器/杀软短暂占用），`writeJsonAtomic` 的 `.tmp-*` 文件在 U 盘上累积了 23 个。
   **修复**：rename 失败重试一次，仍失败则清理临时件。

**结论**：掉盘保护的**安全语义全部成立**（断点保全、停止写入、不自动续传、显式确认、身份校验、最终数据完整）。当时缺口是**恢复效率**——FR-03 分片化已在第二阶段补齐「只重传缺失/截断分片」的能力（§3.15）。

#### 3.15 第二阶段：FR-03 分片级校验续传
**状态：代码已完成，第二阶段收尾时引擎测试 23/23 通过（typecheck 与 build 全绿）；第三阶段新增用例后为 24/24，见 §3.16。真实介质复验已完成，见 §3.17。**

**目标**：解决 §3.14 实测问题 1 —— 整文件粒度下无法定位受损区间，只能整份重传。

**实现方式**：续传粒度从「服务层计算字节偏移」下沉到「工作线程按分片比对」，服务层只负责开关。

| 能力 | 落点 |
| --- | --- |
| 分片比对与只重传受损分片 | `electron/engine/copyWorker.ts` — 默认 1 MiB 块（`DEFAULT_CHUNK_BYTES`），逐块比对目标 `.part` 与源文件的 SHA-256，仅重写不匹配块 |
| 复用边界与截断 | 同上 — 仅当 `offset + length <= existingBytes` 才判定可复用；`.part` 超长时截断到源长度 |
| 写入事实回报 | 同上 — `CopyResult.writtenChunks` / `writtenBytes` 记录实际写入的分片序号与字节数 |
| 校验失败不退整份 | 同上 — `VERIFY_FAILED` 保留临时件供后续显式重试，不截断重传；整文件回读校验通过后才允许提交 rename |
| 续传开关 | `electron/engine/service.ts` — `StartOptions.resume`；`recover()` 以 `resume: true` 调用，正常备份同样为 `true`（故应用崩溃后的普通重跑也可复用分片） |
| 分片粒度可配 | `CopyTask.chunkBytes`，上限 16 MiB；**当前无 UI 暴露，FAT32 自适应未做** |

**验收证据（B3 自动化回归）**：以显式恢复入口构造「账本进度领先 + 分片等长损坏 + 截断 + 缺失」的 `.part`，断言工作线程实际写入记录为分片 1、3、4（0 起编号），共 `2 MiB + 尾块` 字节；分片 0、2 未被重写；最终文件与源文件逐字节一致。落在 `test/engine.test.ts`「B3：显式恢复只重写损坏、截断和缺失的分片」。

**真机演练脚本的度量口径同步**：`test/disk-loss-drill.ts` 的 B3 断言原先读取 `state.summary.copiedBytes`，在新模型下该值是**逻辑进度**（含复用分片），恢复结束时恒等于文件总大小，会把「只重传受损分片」误判为失败。已改为订阅 `copy-completed` 事件累加 worker 上报的 `writtenBytes` / `writtenChunks`，即**真正落到磁盘上的字节**。

进一步的修正：断言不应笼统地要求「写入量 < 总大小」——掉盘时 U 盘的写缓存可能整体丢失，`.part` 一个分片都不可复用，此时全量重写是**正确行为**。现在演练脚本在恢复**之前**先逐片比对 `.part` 与源文件，统计出「可复用 / 损坏 / 缺失」三类分片，再断言：

- 损坏 ∪ 缺失 的分片集合 == 实际重写分片集合（受损分片必须被重写）
- 可复用分片集合 ∩ 实际重写分片集合 == 空（完好分片不得被重写）

这样才能真正区分「分片级续传生效」与「没有可复用分片时的全量重写」。

**与 FR-03 原文的差距（未做）**

- 独立分片文件与逐分片原子 rename：仍以整文件 `.part` + 原子 rename
- 索引事务提交：块级 hash 为运行时比对，不落盘为可审计索引
- 分片大小可配的 UI 入口与 FAT32 自动降级
- 大段写入间主动 sync：当前仅整文件结束时 `fsync` 一次

#### 3.16 第三阶段：掉线后停止写入与介质状态竞态修复

**状态：代码已完成。新增 1 项回归用例，引擎测试 24/24 通过；连续 20 轮压测无偶发失败。**

**发现方式**：「拔盘检测」用例在 12 轮压测中偶发失败（`media` 被从 `lost` 翻回 `online`）。追查后确认是**两个独立问题**叠加。

**问题一：测试时序不可靠（失败表象）**

原用例固定等 120ms 后执行「拔盘」。128 MB 的复制在高速 NVMe 加页缓存下可能**在 120ms 内就已跑完**——备份已经结束，自然不会发生掉线，`media` 停在 `online`。这不是掉线检测失败，而是模拟动作来得太晚。
**修复**：用例改为轮询目标端 `.part`，确认文件**仍在增长**后才执行「拔盘」，确保动作落在写入阶段。

**问题二：掉线后引擎仍写目标盘，并把目标目录「造回来」（真实缺陷）**

`journal.writeMirror()` 会先 `mkdir` 目标端 `.backup-studio` 目录。介质掉线后，账本镜像的周期双写（400ms 一次）会**重新创建出目标目录**；随后的只读探测把这个自己造出来的目录当成「介质可达」，把 `lost` 悄悄翻回 `online`——掉线事实被彻底掩盖，同时违反「掉线后停止写入」。
同类问题也存在于 `onCopyDone()` / `performRename()` / `performDelete()`：三者都是**先 mkdir 再 rename**，介质掉线时同样会重建目标目录。

**修复内容**

| 改动 | 落点 | 说明 |
| --- | --- | --- |
| 镜像写入不再创建目录 | `electron/engine/journal.ts` — `writeMirror()` 改用 `writeJsonAtomic(..., { createDirs: false })` | 父目录不存在即视为「介质已不在」，放弃本次镜像写入 |
| 原子写支持不建目录 | `electron/engine/manifest.ts` — `writeJsonAtomic()` 新增 `createDirs` 选项 | 从根上杜绝「掉线后重建目标端目录」 |
| 掉线后停刷盘上镜像 | `electron/engine/service.ts` — `flushJournal()` 经 `canWriteMirror()` 判定 | 仅在介质在线、目标根可达、身份未漂移时才双写 |
| 提交顺序改为先 rename 后 mkdir | `electron/engine/service.ts` — 新增 `commitToTarget()`，三处提交路径共用 | 补建父目录前先复核目标根可达性；不可达即判定掉线，不重建目录 |
| 掉线后停账本刷盘 | `electron/engine/service.ts` — `handleMediaLoss()` 内 `stopJournalFlush()` | 掉线后本机账本只落一次，不再周期性写盘 |
| 介质「回来」时校验身份 | `electron/engine/service.ts` — 新增 `expectedMedia`（掉线后**不清空**） | 同一路径插入**另一块设备**判为身份漂移，禁止写入，不再当作「介质恢复」 |

**新增回归用例**：「容灾：掉线后不再向目标盘写入，也不会重建目标目录」——掉线后断言目标目录**未被重建**，且状态**不会被翻回** `online`。

**遗留局限**：本阶段的验证手段仍是「删除目标目录」。该手法无法等价复现物理掉线——目录删除后路径仍落在同一文件系统上，某些写入可能仍然成功。真机结论仍以 §3.14 为准。

| B4 内容一致 | ✓ | sha256 `88b05e67a7828b75…` 源与目标完全一致 |

**B3 的真实数据**

恢复前对 `.part` 逐片比对得到：

- `.part` 实际 255 MB（账本记 271 MB —— **账本进度领先于磁盘实际内容**）
- 可复用 183 个 / 损坏 72 个 / 缺失 513 个（合计 768）

恢复时实际写入 **585.0 MB / 768.0 MB**，重写分片 **585 个**，正好等于 72 + 513。

- 183 个完好分片**未被重写**（省下 183 MB 磁盘写入）
- 72 个损坏分片被重写
- 513 个缺失分片被重写
- 恢复耗时 78.0 秒

**第一轮与第二轮的差异**

第一轮（1024 MB）曾观察到「全部 1024 个分片都被重写」，当时判为 B3 失败。事后查明：该轮 `.part` 中**没有任何可复用分片**——U 盘的写缓存整体丢失，`.part` 长度正确但内容全部损坏，全量重写是正确行为。旧断言「写入量 < 总大小」在此场景下不成立，遂改为「受损分片集合 == 实际重写集合 且 完好分片不得被重写」。

**结论**：FR-03 分片级续传在真实移动介质上**生效**，且能显著减少重传量。掉盘后 U 盘丢失的数据范围由设备缓存行为决定，引擎按磁盘实际内容逐片判定，不依赖账本记录。

**仍未验证**

- 本轮未覆盖「同一路径插入另一块设备」的身份漂移判定（需替换设备）
- 未覆盖 `mirror-archive` 模式下的掉盘恢复

**背景**

REQ-AUT-001 的实现只支持**单一配对**（`auto-sync.json` 中 `pair` 为单对象），用户只能把一个源目录映射到一个备份目录。而真实使用场景通常是「多份资料各归其位」：例如 `资料A → 备份盘/资料A`、`资料B → 备份盘/资料B`，需要成对新增，而不是反复改写同一个配对。

同时，删除保护、回收站与版本历史如果只存在于本机状态文件，就无法满足「下次插盘时记录还在」：拔盘换机或重装后，备份介质上应当仍是可核对、可撤回的完整记录，而不是一堆失去上下文的散件。

- 支持同时配置多个「源目录 → 备份目标目录」配对，每个配对拥有**独立的**索引、事件队列、回收站、版本历史与开关；并发与吞吐在所有配对间共享同一上限。

- 本机状态文件仅作加速与离线视图；介质侧记录缺失时能据介质重建，不得因本机文件损坏而丢失介质上已有的记录。

### REQ-MAN-001 手动备份非破坏性默认与回收站

**背景**

可用性审计的 **D-01** 是唯一的 S1 级不可逆数据丢失路径：手动备份默认使用「严格镜像」，会把目标端多余文件直接 `unlink` 掉；删除确认门槛是「源文件数为 0 / 孤儿率 > 30% / 删除数 > max(100, 源文件数)」，典型场景（源 5000、孤儿 200）根本不弹确认；删除既无回收站也无撤销；主状态行只说「将写入 N 个文件」，从不提删除。

三个要素叠在一起，「备份 = 拷贝」的心智就不成立：用户以为在拷贝，实际在删除，且删掉的内容再也找不回来。

**需求描述**

- **默认语义改为非破坏性**：新增 `SyncMode = 'copy'`（只做新增/更新/改名，目标端多余文件一律保留），并作为手动备份的默认模式。破坏性的镜像语义保留，但必须由用户显式选择。
- **三档同步方式**：`copy`（非破坏性，默认）/ `mirror-archive`（安全镜像：删除的内容进入回收站，可还原）/ `mirror`（严格镜像：删除且不留副本，不可恢复）。每个选项都必须在自己的文案里写明后果。
- **删除确认门槛下调为「删除数 > 0 即确认」**：旧的 30% 孤儿率门槛让「删掉 1 个文件」在正常同步里静默发生。删除数量异常偏多时，确认文案额外提示源目录与目标目录可能选错。
- **手动备份回收站**：删除动作的内容先落到归档副本再从原位移除，并登记进可浏览的索引；界面提供「还原」与「彻底删除」。还原是一次真实写入，必须走与备份相同的写入闸门；目标位置已被占用时默认拒绝，只有用户显式确认覆盖才写入。
- **可见性**：计划区在存在删除动作时给出醒目提示并区分可恢复与不可恢复；主状态行在就绪态与完成态都显式给出删除数与保留数。

**验收标准**

- [x] 默认同步方式为非破坏性：源端删除的文件在目标端原样保留，计划中不出现删除动作
- [x] 非破坏性模式下新增、更新、改名照常执行
- [x] 被保留的文件不写入备份清单（不会在下一轮被当成已备份内容参与快判）
- [x] 删除数 > 0 即触发二次确认（删除 1 个文件、孤儿率 1% 的场景不再静默通过）
- [x] 安全镜像下被删除的内容进入回收站，可还原且内容一致，还原后条目移除
- [x] 还原时目标位置被占用会拒绝；显式确认覆盖后才写入
- [x] 彻底删除回收项后归档副本一并消失

### REQ-DUP-001 重复文件检测与清理

| 字段 | 内容 |
| --- | --- |
| 状态 | 已实现（2026-11-20 落地；2026-11-21 合入 PR #2 后完成缺陷修复与独立审查） |
| 优先级 | P1（P0 FR 已就绪，可与 REQ-AUT-001 剩余面并行） |
| 所属模块 | 引擎 / 界面 |
| 提出日期 | 2026-11-20 |
| 关联代码 | `electron/engine/dup/**`、`shared/dup-types.ts`、`electron/main.ts`、`electron/preload.ts`、`src/components/DuplicateFinder/**`、`src/App.tsx`、`test/dup.test.ts` |

**背景**

备份引擎的去重只发生在「源端 ↔ 目标端」配对时，目标端遗留的同内容副本从不被提示；而「重复占空间」是本地目录最常见的浪费来源，当前软件对此完全没有出口。

**需求描述**

- 标题栏**独立按键** → 进入**全屏独立页面**；选目录后递归检测
- 结果分两类：**内容重复（哈希相同，不论文件名是否相同）**与**同名但内容不同**（单独告警区，整页提示内容不一致）
- 每条结果提供 **保留 / 删除 / 下次不提醒**；组级提供「保留此份，其余可删」「整组不再提醒」
- 删除落 **系统回收站**（不可用时降级本机隔离区，可还原），并执行**删除前二次校验**
- 「下次不提醒」以**内容哈希**入黑名单，下次扫描跳过整组；**撤销入口为检测页顶部「抑制清单 (N)」**，支持逐条与全部撤销
- 双击结果中的**文件绝对路径**打开其所在目录
- 判定走三级漏斗（大小分桶 → 首尾 64 KiB 局部哈希 → 全量 SHA-256）；大文件标「疑似重复（未全量校验）」
- 删除属写操作，**复用统一写入闸门**，并与备份/自动同步互斥；任一组**至少保留一份**

**验收标准**

- [x] 两类结果物理分离，重名类默认不预选任何删除项并带内容不一致告警（`test/dup.test.ts` §11-3）
- [x] 删除进系统回收站且可还原；扫描后被修改的文件被二次校验拦下（§11-8、§11-9）
- [x] 介质异常或备份运行中时删除被拒并说明原因（§11-10、§11-11）
- [x] 抑制黑名单生效、抑制清单可逐条撤销与全部撤销，撤销后重新提示（§11-13、§11-14）
- [x] 双击路径可在文件管理器中定位；伪造路径请求被主进程拒绝（FR-14 边界校验 + §11-15）
- [x] 界面不出现任何永久删除入口（落地只有「系统回收站 / 本机隔离区」两种）
- [x] 抑制只影响检测页提示，**不改变备份写什么**（P-03 回归：`P-03-1`／`P-03-2`／`P-03-3`）
- [x] 每组至少保留一份在**跨多轮删除**与**同名告警组并存**两种情形下都成立（FR-11 回归）
- [x] 隔离区降级后条目**可列出、可还原**，且还原走写入闸门、目标被占用时拒绝静默覆盖（FR-08 回归）

### 3.19 逻辑健康检测与人工修复入口（2026-11-20）

- **FR-06**：`health.ts` 汇聚只读卷/磁盘状态、NTFS 脏位、MBR 条目边界/GPT 主备头与条目 CRC32、NTFS 启动扇区签名、备份文件 SHA-256 及权威账本/盘上镜像比对。Windows 使用 `Get-Volume`、`Get-Partition`、`Get-Disk`、`Win32_Volume.DirtyBitSet`，必要时使用 `fsutil dirty query`；`Get-StorageReliabilityCounter` 仅在可确认对应磁盘且有权限时建立会话内基线。权限不足、计数不可用或桥接不透传，明确显示「能力缺失」。
- **FR-09**：`repair.ts` 仅提供演练；选择作用卷、二次确认并接受免责后，重新只读预检、保存 Windows NTFS 卷首尾扇区及本机审计。审计含确认、范围、镜像相对路径及 `command: null`。它不是完整卷镜像。分区表仅导出证据至本机 `userData/evidence` 并提示人工核查；没有分区写回或文件系统修复命令。
- **FR-11**：`service.ts` 刷新应用侧枚举和分层证据，提示换口、换线、换主机；持续不可达或硬性介质风险进入可撤销的隔离观察。分层校验通过后淘汰旧计划；保留本机中断账本，不自动续传。
- **FR-15**：`security.ts` 用当前进程权限判定，不自动提权；固定只读程序与参数、校验盘符和磁盘号、不经过 shell。事件日志默认脱敏常见凭据和已知用户路径；`BACKUP_STUDIO_LOG_PATHS=1` 只允许诊断环境保留路径，不关闭凭据脱敏。
- **FR-16**：`capability.ts` 提供 72 个结构化组合，主界面按平台查看。以下为随版本发布的矩阵，表中每个文件系统单元格同样适用于该行的三个独立接口组合。

| 平台 | 接口 | NTFS | ext4 | exFAT | APFS | FAT32 |
| --- | --- | --- | --- | --- | --- | --- |
| Windows | USB 桥接 / SATA / NVMe | 可检测 / 可自动处理 | 不支持 | 可检测 / 可自动处理 | 不支持 | 可检测 / 可自动处理 |
| Linux | USB 桥接 / SATA / NVMe | 不支持 | 仅告警 / 可自动处理 | 仅告警 / 可自动处理 | 不支持 | 仅告警 / 可自动处理 |
| macOS | USB 桥接 / SATA / NVMe | 不支持 | 不支持 | 仅告警 / 可自动处理 | 仅告警 / 可自动处理 | 仅告警 / 可自动处理 |

前一状态指设备/卷级检测，后一状态仅指 OS 已挂载目录上的应用备份集能力，并非自动盘修复。各平台和接口均不支持应用内直接修复；加密容器、VHD、压缩包内文件系统均不支持直接 fsck，也不提供容器内部流式断点续传。本版本不写入或废弃任何完整备份集来弥补这些能力缺口。

**验收边界**：`typecheck`（三套配置）、`build:electron`、`test:engine`（35/35，新增 11 项）、`build` 与 `git diff --check` 通过。测试覆盖只读探测、MBR/GPT 校验、确认与镜像顺序、隔离撤销、权限和矩阵。实际 Windows 原始设备镜像、高权限可靠性采集及 Linux/macOS 的原始文件系统诊断未真机验收。（合并 PR #1 后引擎测试为 42/42，见 §6 变更记录）
