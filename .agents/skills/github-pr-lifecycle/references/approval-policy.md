# GitHub Review、审批与合并授权

本文件适用于 `Su-Qingmu/backup-studio` 的 `github-pr-lifecycle` 工作流，规定 Agent 何时可以给出审查建议、提交正式 Review、修复 PR 或执行合并。合并门禁及其验证步骤见 [合并与门禁策略](./merge-policy.md)。

## 三层审查与审批

| 层级 | 谁产生 | 记在哪里 | Agent 能否替代 | 何时不可继续使用 |
| --- | --- | --- | --- | --- |
| Agent 内部审查结论 | 主 Agent 或独立只读复审的 Sub-agent | 审查报告，关联 PR 编号、Head SHA、证据和发现编号 | Agent 可以自主审查并给出建议。内部结论不产生 GitHub Review 或正式审批 | Head SHA 变化后须重新审查。已有证据不足以支撑原结论时须重核 |
| GitHub 正式 Review | 经用户授权并有权执行该动作的当前 GitHub 账号 | 目标 PR 的 GitHub Review 记录，含提交者、状态和 `commit_id` | Agent 可用获授权的当前账号提交。不得冒用其他真人、团队成员或独立审查者的身份 | 历史记录可以保留，但其结论只覆盖绑定的提交。Head SHA 更新后，旧 `APPROVED` 不得作为新版本获批的证据。被撤销的 Review 不再作为有效审批 |
| 仓库保护规则要求的正式审批 | 符合当前规则的审查者，是否计入由 GitHub 按适用规则判定 | 目标 PR 中符合规则的正式审批及当前门禁状态 | Agent 不得替代规则要求的独立审查者、指定审查者或审批数量。用户授权也不能代替这些条件 | 被撤销、被标记过时、因规则变化而不再计入，或无法覆盖当前 Head SHA 时，均不得视为满足 |

本仓库的关键工作流采用独立只读复审，记录 `VERDICT: FAIL` 或 `VERDICT: PASS`，发现按 `C1`、`H1`、`M2` 等编号。每轮修复后，独立复审须收窄到本轮改动与受影响的边界，并核实相关发现是否关闭。该复审属于 Agent 内部审查，`VERDICT: PASS` 不构成 GitHub 正式 Review 或仓库保护规则要求的审批。

## 操作模式

| 模式 | 允许的动作 | 禁止的动作 | 授权要求和指令示例 |
| --- | --- | --- | --- |
| Mode A：Review Only | 只读审查、检查证据、生成内部结论和 Review 草稿 | 提交正式 Review、修改代码、合并 | 默认模式。用户说“帮我审查一下。”或“准备合并。”时，只做审查或只读合并准备 |
| Mode B：Review and Fix | 审查并在目标 PR 的来源分支做必要修复，提交前检查远程分支，修复后重新审查 | 修改或直接推送 `main`、强制推送、覆盖用户已有工作、修改无关业务模块。该模式本身不授权正式 Review 或合并 | 用户须授权修复该 PR 的来源分支。例如“审查 PR #16，把必要修复提交到它的来源分支。” |
| Mode C：Review and Approve | 完成审查后，在用户当前授权范围内提交相应的正式 GitHub Review，包括 Approve、Request Changes 或 Comment | 未获授权提交 Review、换发未获授权的 Review 类型、自批、合并。该模式本身不授权修复 | 需要对目标 PR 当前审查版本和提交动作的明确授权。例如“审查 PR #16，符合批准条件就提交正式 Approve。” |
| Mode D：Review and Merge | 完成审查，确认当前有效的审批情况及全部合并门禁后，合并指定 PR | 未经明确授权合并、擅自提交正式 Review、擅自修改来源分支、擅自改走本地合并并推送 `main` | 必须获得对本次 PR 当前审查版本的明确合并授权。例如“合并 PR #16。”如需由 Agent 新提交正式 Review 或修复代码，对应动作须有独立、明确的授权，可在同一句指令中给出 |

## 明确授权的判定与时效

> **每次开始新的 PR 任务，都必须重新检查本地与远程仓库状态**，重新确认 PR 当前的 Head SHA、状态与 Review 记录。不得沿用上一次任务的检查结果；上一轮的审查结论、Approve 与合并授权都不自动适用于本轮的新版本。

以下是明确合并授权示例：

- “合并 PR #16。”
- “按照你给出的条件，直接合并这个 PR。”
- “批准并合并当前这个 PR。”

以下均不构成合并授权：

- “看看这个 PR。”
- “帮我审查一下。”
- “准备合并。”
- “给我合并建议。”

1. 授权必须绑定**明确的 PR 编号和当前审查版本的完整 Head SHA**，并限定获授权的动作。用户可以用“这个 PR”或“当前这个 PR”指代上下文中唯一明确的 PR。Agent 必须在执行前记录指令对应的仓库、PR 编号、审查所依据的 Head SHA，以及获授权的动作和条件。不能唯一确定 PR、审查版本或动作时，先请用户澄清，暂停相应写操作。
2. “按照你给出的条件”只授权在这些条件均已满足时合并。“批准并合并”明确授权两项操作，但两项都须满足各自的前提。单独的合并授权不授权代为提交 Approve，也不授权修复或直接推送 `main`。内部 Approve 建议、有效的 GitHub 审批和技术上能够合并，均不构成用户合并授权。
3. **授权后 Head SHA 发生变化，原授权失效。** 停止提交正式 Review 和合并，重新审查新版本并重核证据。若要继续提交正式 Review 或执行合并，必须重新取得绑定新 Head SHA 的明确授权。只做内部复审和报告时可直接继续。作者推送、rebase 或 Agent 修复产生的新提交均适用此规则。Mode B 对当前修复轮次的授权只允许提交和推送该轮已授权修复，不会把原有的 Review 或合并授权传递给修复后的版本。

## Review 决策与正文要求

### Approve

只有同时满足以下七项条件，才可以建议 Approve：

1. 审查已经完成。
2. 没有未解决的 Critical 或 High 问题。
3. 重要 Medium 问题已经修复，或有明确、可接受的例外理由。
4. 代码符合项目架构约定。
5. 测试结果足以支撑本次变更。
6. CI 状态已经检查。
7. PR Head SHA 与审查依据一致。

正文须写明本次审查的 Head SHA、范围、测试结果和 CI 状态。列出关键发现的关闭证据。若重要 Medium 问题按例外接受，逐条记录编号、接受理由和剩余影响。

### Request Changes

存在以下任一情况，应建议 Request Changes：

1. 存在 Critical 或 High 问题。
2. 核心功能缺陷未修复。
3. 存在明显安全问题。
4. 关键测试缺失。
5. PR 修改不符合预期。
6. 需要作者修改后重新审查。

正文须按编号说明每个阻塞项的严重级别、文件与行号或可定位的验证缺口、触发条件、证据、实际影响、要求的修复及可核验的验收条件。写明作者修改后需要复审的内容。意见必须具体、可执行。`REQUEST_CHANGES` 表示要求作者修改并重新送审，不表达批准。

### Comment

以下场景适用 Comment：

1. 有建议但不阻止合并。
2. 需要作者确认设计选择。
3. 发现潜在问题但证据不足。
4. 需要记录额外验证要求。

正文须给出对应的建议、明确的问题、尚缺的证据或待执行的验证，并写明后续动作及是否尚有未决事项。不得把已确认的阻塞问题降为非阻塞建议，也不得用 Comment 表达或替代正式 Approve。正式 `COMMENT` Review 和普通 PR 评论是不同记录，二者均不构成审批。

## 正式 Review 的提交与核实

正式 Review 提交**优先使用 `gh` CLI**（`gh pr review` / `gh api`，token 注入方式见 [SKILL.md 0.2](../SKILL.md)）；**仅当本机未安装 `gh` CLI 时**，通过 GitHub REST API 提交。无论走哪条路径，必须遵守以下顺序：

1. **核对目标、授权和权限。** 回读 `GET /repos/{owner}/{repo}/pulls/{number}`，确认是获授权的仓库和 PR、PR 仍为 `open`、`head.sha` 与审查及授权一致。核对当前 GitHub 登录身份与 PR 的 `user.login`，并核实目标分支适用规则及是否需要独立审批。无法确认任一必要前提时停止写入。不得对其他 PR 或其他仓库执行操作。
2. **构造正文并固定提交。** 按上述决策要求写 `body`，以 `C1`、`H1`、`M2` 等编号组织发现，填入审查所依据的完整 SHA 作为 `commit_id`。选择与实际结论和用户授权均一致的 `event`。用户只授权 Approve 而审查应判 Request Changes 时，报告内部结论。提交 Request Changes 或 Comment 须另有相应授权。
3. **提交指定事件。** 调用 `POST /repos/{owner}/{repo}/pulls/{number}/reviews`，发送 `commit_id`、`body` 和 `event`。`event` 为 `APPROVE`、`REQUEST_CHANGES` 或 `COMMENT`。紧接写入前再确认 PR 仍为 `open` 且 Head SHA 未变。不得省略 `commit_id` 以接受平台默认版本。
4. **回读实际记录。** 用响应中的 Review ID 调用 `GET /repos/{owner}/{repo}/pulls/{number}/reviews/{review_id}`，核实提交者、`commit_id` 及对应状态 `APPROVED`、`CHANGES_REQUESTED` 或 `COMMENTED`。再次读取 PR 的 Head SHA，确认结论仍覆盖当前版本。请求已发送、HTTP 成功或内部结论已生成，均不足以宣称 Review 已按预期落库。若响应不明或回读失败，先核对已有记录，禁止盲目重发。若回读证明 Review 落在旧版本，只能报告旧版本的实际记录，随后按授权失效规则处理。

Review 绑定提交时所审查的 `commit_id`。PR 推送新提交后，即使 GitHub 继续显示旧 `APPROVED`，也不得视为新版本已获批准。正式 Review 落库和该 Review 满足仓库保护规则，必须分别确认。

## 自审、自批和等待边界

- 本仓库使用 GitHub 主账号 `Su-Qingmu`。以 API 的 PR 作者和当前认证身份为准。协作者将分支推到主账号名下并由主账号开 PR，或用户自行开 PR，都可能使当前账号成为 PR 作者。当前账号就是作者，或仓库规则禁止自审、自批时，停止被禁止的正式自审、自批，不得尝试绕过限制、伪造他人审批或将普通评论冒充正式 Approve。必须如实报告“需要独立 Review”及其原因。
- 不得把内部审查、Sub-agent 复审或普通评论冒充 GitHub 正式 Review。不得冒用其他账号、代表其他真人或团队作出审批，也不得通过改变保护规则、管理员绕过或其他操作规避适用门禁。
- 对他人发起或持有来源分支的 PR，在操作前确认 PR 编号、来源仓库和分支，并核实该动作的授权及当前账号权限。不得向相似分支、其他 PR 或未经授权的远端写入，也不得因能写入便推定获得授权。
- 等待协作者 PR 时，在 `docs/TODO.md` 新建（或复用）「等待协作者 PR 的后续项」小节登记待修问题和触发条件，然后正常结束回合。**该小节当前不存在**（PR #2 合入后已随相关条目一并结清），需要时按 `docs/REQUIREMENTS-003-DUPLICATE-FINDER.md` 中既有的引用方式补建。等用户告知 PR 已合入后再动手。不得创建定时任务、自动提醒或轮询来等待协作者 PR。

## 修复协调（Mode B）

1. 优先实施足以解决审查发现的最小修改，遵循项目现有约定。
2. 只在已获授权的 PR 来源分支修改，不做无关重构，不修改或推送 `main`，不擅自修改与 PR 无关的业务模块。
3. 不覆盖用户已有工作，不强制推送。提交前再次检查远程来源分支，核对仓库、分支和远端 SHA。推送前复核远端未发生并发变化。发现远端已有新工作或无法确认工作是否会被覆盖时停止，并报告冲突或变化，不得用强制推送处理。
4. 需要 Sub-agent 修改时，明确分配文件所有权，写明各自可修改的文件。文件写入权限不得重叠。调度见 [Sub-agent 调度策略](./subagent-policy.md)。
5. 修复范围明显超出 PR 原始目标时，先报告超出项及原因，等待用户决定是否扩大范围。未获同意不得实施超出部分。
6. 修复后重新检查完整相关 Diff，重新执行适用测试，并重新审查。每轮修复后按仓库独立只读复审惯例收窄复审范围。收窄独立复审不取消主 Agent 对完整相关 Diff 的检查。修复前的 Approve 结论失效，必须以修复后版本的证据重新作出结论。

## Mode D 的合并授权与路径

本仓库记录的设置为：`main` 没有分支保护规则，`GET /branches/main/protection` 返回 `404`。`allow_squash_merge`、`allow_merge_commit` 和 `allow_rebase_merge` 均为 `true`，`delete_branch_on_merge` 为 `false`。执行时须用有足够读取权限的身份复核当前设置、适用的规则集和 Required Checks。历史 `404` 不视为放行依据，也不能仅凭 `404` 断定没有适用规则。

| 合并路径 | 执行及记录差异 | 授权条件 |
| --- | --- | --- |
| GitHub 合并按钮对应的 PR 合并 API | 默认且优先的路径。走 `PUT /repos/{owner}/{repo}/pulls/{number}/merge`，提交审查过的 `sha` 作为版本前提，由 GitHub 执行适用门禁并记录合并结果 | 对该 PR 当前 Head SHA 的明确合并授权，且所有适用门禁均已满足 |
| 本地合并后推送 `main` | 直接更新目标分支，风险更高，因为这条路径可绕开 PR 的 Required Checks 或分支保护流程。GitHub 可以随分支更新自动关闭 PR，历史上出现仅 `closed` 而未记录 `merged` 的情形。平台是否识别为已合并须实查 | 只有用户明确指定本地合并并推送 `main`，且已证实通过 PR 路径确实无法满足分支保护或 Required Checks 流程时，才可考虑。必须在执行前报告无法走默认路径的原因、未能满足的流程及偏差，并在结果中记录。该授权不允许绕过仍适用的保护规则或跳过未通过的检查。检查失败、冲突、审批缺失或无法核清门禁时必须停止。不得因 GitHub 合并被拒而自行改走本地路径 |

历史 PR #1、#2 走的是本地合并后推送 `main` 的路径，曾呈现 `closed` 而非 `merged`。#2 是零冲突快进合入。#1 因贡献者 rebase 后 force-push，PR Head 不在 base 历史中，GitHub 起初未认作 `merged`，本地用 `git merge -s ours` 记录合并关系后才被 GitHub 标记为已合并。该历史操作不能作为本流程的自动回退手段。`ours` 记录的祖先关系本身不证明目标内容已应用。

合并后必须核实**远端目标分支历史包含本次实际合并结果的提交**。快进核对合入的 Head SHA，合并提交核对实际生成的合并 SHA，squash 或 rebase 核对目标分支上的对应结果提交。若历史记录只证明建立了合并关系，还须核对预期改动确已纳入。分别报告目标分支的核实证据与 GitHub 的 PR 状态。不得仅凭 `merged` 字段判定是否真正合入，也不得仅凭 `closed` 认定未合入或已合入。

取得明确授权后，确认当前版本的审查已完成、所需审批有效，并完成 [合并与门禁策略](./merge-policy.md) 的 12 条门禁检查。实际写入前复核目标 PR、Head SHA、授权和合并路径。合并过程中发现新风险、CI 状态变化、分支冲突或审批失效，必须立即停止，报告变化并重新核验门禁。若 Head SHA 变化，原授权失效，重新审查并取得新版本授权后才能恢复写入。合并请求结果不明时，先核实 PR 和远端目标分支实际状态，不得直接重试或改走另一条路径。

## 指令路由

1. **能唯一确定目标 PR 吗？** 不能 → 先问仓库和 PR 编号，不写入。能 → 确认当前 Head SHA 并开展只读审查。
2. **用户只要求查看、审查、准备合并或给建议吗？** 是 → Mode A，交付内部结论。用户明确要求修复来源分支 → 执行 Mode B 的已授权修复，修复后重新审查。
3. **用户明确授权提交正式 Review 吗？** 否 → 只交付建议，不提交 Review。若合并需要额外审批，报告缺少的审批。是 → 按 Mode C 核对当前版本、实际审查结论、事件授权和身份规则。缺授权的事件先问，需要独立 Review 时报告原因，由符合条件的审查者处理。
4. **用户明确授权合并这个 PR 的当前版本吗？** 否 → 不合并。若任务要求执行合并，请用户明确授权。是 → 进入 Mode D。默认走 GitHub 合并 API，本地路径需另有明确指定并符合例外条件。审批和门禁都通过才执行。
5. **写入前 Head SHA 变了，或执行中出现新风险、CI 状态变化、冲突或审批失效吗？** 是 → 停止。重新核对相关证据和门禁。版本变化时重新审查，继续提交正式 Review 或合并前须取得新版本授权。否 → 执行获授权的动作并回读验证结果。
